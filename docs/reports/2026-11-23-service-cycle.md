# 운동 추천·카메라·개인화 흐름 개편 작업 보고서

작성일: 2026-11-23
보완일: 2026-11-24 — 판정기·정책 적용 단위·검사 범위와 팀 확인 항목 명시
작업 위치: `codex/survey-v2` 로컬 작업 트리
기준: 개편 계획 2판과 이후 이형민이 확정한 횟수·휴식·무릎 제한·차트 계산식

## 적용한 흐름

저장 조건 확인 → 오늘 컨디션 선택 → 카메라 준비와 생성 작업 동시 진행 → 루틴 확인 → 5단계 운동과 휴식 → 만족도 조사/건너뛰기 → 프로필·다음 추천으로 연결했다. 검정 배경, 빨강 강조, Wanted Sans를 유지했다.

- 사전조사: 목표·경험·일정·8개 제한 부위와 좌우/정도·6개 우선 부위를 저장한다. 현재 수준과 사전조사의 선호 강도는 없앴다. 저장 조건은 재조회·버전 충돌·응답 유실 재시도를 지원한다.
- 준비: `/prepare?requestId=…`에서 카메라와 생성 상태를 함께 확인한다. 생성 완료만으로 운동을 시작하지 않는다. 사용자가 루틴을 확인하고 카메라에 준비 자세가 잡힌 뒤 시작한다. 카메라 권한이 없으면 시작할 수 없다. 준비 화면 주소와 권한 거절 시 시작 차단은 **구현 결정, 팀 확인 필요**다.
- 생성: 서버가 제한 조건, 경험, 직전 결과와 설문으로 허용 운동·횟수를 정한다. Gemini에 이 범위와 목표·확인한 키워드만 보내 5단계와 설명 ID를 받는다. 운동 ID·횟수·단계 순서가 서버 계획과 다르면 저장하지 않는다. 설명은 자유 문장을 받지 않는다. 모델은 `steady`·`habit`·`control` 중 하나의 설명 ID만 반환하고, 서버가 해당 ID에 미리 정해 둔 문장을 저장·표시한다. 허용하지 않은 ID는 거절한다. 운동별 시작 자세·실수·중단 조건은 별도 카탈로그 문장을 사용한다.
- 운동: 운동명, 목표, 현재 단계, 남은 횟수, 카메라 상태를 표시한다. 휴식은 건너뛰거나 늘릴 수 있다. 휴식 중 반복은 DB에서도 거절한다. 휴식 시작·종료 시각을 DB에 저장해 재접속해도 이어가는 처리는 **구현 결정, 팀 확인 필요**다. 횟수 이벤트는 멱등 키와 버전으로 중복·충돌을 막는다.
- 누락/중단: 카메라 판정 불가는 반복을 더하지 않고 기존 단계·횟수를 유지한다. 미완성 왕복은 버린다. 추적 누락·통증 중단은 다음 추천에서 실패로 취급하지 않고 보석 손상도 적용하지 않는다.
- 설문: 강도·시간·만족도·자유 의견, 선호 칩을 모두 선택 입력으로 받는다. 빈 제출은 건너뛰기로 저장한다. 완료 세션의 본인만 한 번 제출할 수 있다. 제출 응답 유실은 같은 키로 복구한다.
- 자유 의견: 서버 규칙으로 후보 키워드를 보여 주고 사용자가 직접 고른 키워드만 저장·전송한다. 통증 문장은 선호 키워드로 추출하지 않고 조건 수정으로 안내한다. 이름·연락처·키·몸무게·제한 원문·의견 원문은 새 생성 요청에 보내지 않는다.
- 프로필: 실제 기록으로 육각형 지표를 계산한다. 3회 미만은 기록 수집 중이며, 근거가 부족한 축은 null/자료 없음이다. 낮은 데이터 수를 0점으로 채우지 않는다.
- 경로 정리: 갤러리·디자인 미리보기·별도 준비 시안은 404로 닫았다. ID가 없는 운동·완료 화면은 가짜 예시 대신 홈으로 돌아간다. `/survey/legacy`는 새 조사로 이동한다(**구현 결정, 팀 확인 필요**). 과거 운동의 실제 조회·재개·결과·설문 경로와 v1 데이터는 유지했다. 홈에서 기존 진행 중 운동도 이어갈 수 있고 v1/v2가 동시에 시작되지 않도록 같은 사용자 잠금을 사용한다.

## 확정값과 이번 구현의 보수적 기본값

| 항목 | 적용값 | 구분 |
| --- | --- | --- |
| 초보자 상한 | 단계당 15회 | 이형민 확정 |
| 휴식 상한 | 단계 사이 휴식 1회당 최대 1,800초(30분). 연장분 포함 | 30분은 이형민 확정. 1회 기준 적용은 구현 결정, 팀 확인 필요 |
| 무릎 통증 | 정도·좌우와 관계없이 무릎 푸시업 제외 | 이형민 확정 |
| 첫 운동 | 초보 무릎 3회, 가끔 정자세 4회, 꾸준히 정자세 6회 × 5단계 | 2판 결정 |
| 증감·승급 | 쉬움+달성 +1, 어려움/미달 −1, 무릎 6→정자세 2, 정자세 2 어려움→무릎 6 | 2판 결정 |
| 기본 휴식 | 60초. 확인한 휴식 칩에 따라 45/75초 | 구현 초기값. 임상 기준 아님 |
| 비초보 상한 | 우선 15회로 제한 | 더 높은 상한을 임의로 만들지 않은 보수적 제한 |
| 보통/심한 제한 | 해당 관절을 쓰는 후보 제외 | 낮은 부하를 허용할 근거표가 아직 없으므로 보수적으로 처리 |
| 약한 제한 | 해당 운동의 이번 횟수를 20% 낮춤. 최소 1회 | 2판의 감량 원칙에 대한 초기 수치 |
| 무릎 푸시업 불가인 초보 | 일반 푸시업으로 강제 승격하지 않고 후보 없음 안내 | 구현 결정 |
| 보석 달성률 | 50/70/80%, 비초보 연속 3회 미달부터 `dull`(광택 없음) | 2판 제안값과 구현 초기값. `matte` 이미지로 표시하며 흠집·깨짐 상태는 적용하지 않음 |

휴식 30분은 세션 전체 휴식의 합계가 아니다. 각 휴식의 시작 시각(`rest_started_at`)부터 종료 시각(`rest_until`)까지 최대 30분이며, 여러 번 연장해도 그 휴식의 시작 시각 +30분을 넘지 않는다. 다음 단계 뒤에 시작하는 휴식은 새로 계산한다. 기본 휴식은 아래의 45~75초 정책을 따른다.

정책 버전은 `cycle-2026-11-23.1`이다. 진단이나 의학적으로 검증된 운동 처방이라는 의미는 아니다. 근력·체력 목표는 이번 목표만 단계당 +1회(상한 이내), 휴식은 근력 75초·체력/체중 관리 45초·습관 60초를 초기값으로 쓴다. 운동 시간 응답은 길었음 −15초·짧았음 +15초로 휴식만 조정하며 명시적인 휴식 칩을 우선한다. 이 값은 기준 횟수와 난이도 사다리를 바꾸지 않는다. 다른 부위 추천·순환은 운동 종류와 근거표가 늘기 전까지 적용하지 않는다. 관련 선호는 저장하되, 아직 적용하지 않은 효과를 개인화된 결과처럼 표시하지 않는다.

## 육각형 계산

서버 계산 버전은 `growth-1`이다. 모든 값은 0~100 범위로 제한한다.

| 축 | 계산 |
| --- | --- |
| 근력 | 같은 자세의 첫 기록 대비 최근 한 단계 최대 실제 횟수 변화. 기준 50, 두 배 100. 무릎→정자세 승급은 별도 표시 |
| 지구력 | 평가 가능한 기록에서 목표를 채운 단계 / 전체 목표 단계 × 100. 추적 누락·통증 중단 제외 |
| 회복력 | 어려움/미달 뒤 7일 안에 다시 운동한 비율. 아직 7일이 지나지 않은 기록 제외. 생리적 회복 점수가 아님 |
| 꾸준함 | 이번 주 실제 운동한 날짜 수 / 주당 목표 횟수 × 100. 같은 날 여러 번은 하루로 계산 |
| 활동량 | 최근 7일의 측정된 반복 사이 활동 시간과 직전 4주의 주간 평균 비교. 기준 50, 두 배 100. 35일 기준 자료가 없으면 null |
| 강도 | 최근 단계당 목표 / 경험별 적용 상한 × 100. 높을수록 좋다는 순위가 아님 |

활동 시간은 카메라가 인정한 반복 사이의 구간만 합산하고 한 구간 최대 5초로 제한한다. 휴식·일시정지·추적 누락을 운동 시간으로 더하지 않는다. 전체 실제 운동 시간을 완벽히 측정한 값은 아니다.

## 데이터와 배포

새 흐름은 별도 `private.cycle_*` 테이블을 사용한다. 기존 v1 생성·세션을 바꾸지 않으며, 새로운 요청은 상세 사전조사 v2의 ID·버전·답변 스냅샷을 보관한다. 따라서 같은 행에 v1/v2 외래키 두 개를 놓지 않고 새 요청은 v2만 참조한다. 앱 계정은 테이블 직접 쓰기 권한 없이 검증 함수로만 변경한다. worker는 기존 제한된 `generation_worker` 실행 권한을 사용한다.

새 migration:

- `supabase/migrations/20261123000000_add_detailed_survey_v2.sql`: 상세 조사 저장
- `supabase/migrations/20261123010000_service_cycle.sql`: 2판 조사 검증, 새 흐름, worker 확장

운영 DB에는 적용하지 않았다. 운영 반영 시 두 migration과 백엔드·프론트를 함께 올리고 기존 worker의 DB 권한 스크립트도 적용해야 한다. Gemini worker 설정이 없거나 실패하면 생성 성공을 가장하지 않는다. 생성 대기는 5분 후 실패로 처리한다. 기본값과 정책 변경은 다음 생성에만 반영되고 이미 만든 요청의 스냅샷은 유지한다.

## 검증 결과

- 백엔드 전체 332개 검사 통과 후, 후속 변경에 대해 상태·세션·조사·개인화 관련 96개 회귀 검사를 다시 통과했다. PostgreSQL Testcontainers에서 실제 SQL·권한·멱등 처리를 검사했다.
- 추가로 난이도 승급/강등, 초보 상한 15회, 최소 1회, 설문 건너뛰기, 추적 누락/통증 예외, 휴식 1회당 연장분 포함 30분 상한, 모델의 잘못된 운동/횟수·임대 토큰을 검사했다.
- 프론트 단위 검사 205개, lint, typecheck, 생산 빌드 통과.
- 일반 브라우저 검사 30개 통과. 320px 화면, 로그인 실패, 삭제한 시안 주소, 중복 입력 경로, 검정 배경·Wanted 폰트를 확인했다.
- 실제 DB를 이용한 브라우저 검사 34개 통과. 새 흐름의 저장·개인화, 기존 운동 재개, 추적 단절, 중복 요청, 휴식·일시정지 처리를 데스크톱과 모바일에서 확인했다.

브라우저 통합 검사는 임시 JWT, 실제 Spring·PostgreSQL, 합성 카메라 좌표, 테스트 전용 생성 응답을 사용한다. 실제 Google 로그인·Gemini 호출·사람의 운동 인식 검증과 구분한다. 빌드는 기존 Next.js 보안 권고로 첫 실행이 중단됐고 재실행은 통과했다. 이를 보안 문제가 해결된 것으로 기록하지 않는다.

## 카메라 비교와 남은 확인

**현재 로컬 구현의 새 운동 경로 `/workout?cycleId=…`는 관절 기반 `FrontalPushupCounter`만 사용한다. 선택 키는 `frontal-pushup`, ID·버전은 `FRONTAL_PUSHUP_VERSION = "frontal-shoulder-1-candidate"`이며 픽셀 방식으로 자동 전환하지 않는다.** 준비 화면도 같은 판정기를 사용한다. 이 판정기의 추적 조건을 충족하지 못하면 ‘판정 불가’로 표시하고 저장된 횟수·단계를 유지한다. 실제 영상 검증이 부족하므로 계획의 첫 완료 지점인 ‘정면 카메라로 실제로 센다’는 아직 완료로 처리하지 않는다.

기존 세션 재개용 `/workout?sessionId=…`와 `connected=1` 경로는 기존 `ConnectedWorkout`을 유지한다. 이 경로의 푸시업 기본 판정은 `push-up-motion` 픽셀 방식이며 서버에 설정한 카메라 규칙에 따라 관절 각도 방식을 사용할 수도 있다. 따라서 위의 단일 판정기 선택은 **새 흐름에 한정**된다. 제품 전체를 하나로 통일하는 것은 기존 세션 호환 처리와 함께 팀 확인이 필요하다.

새 판정 후보 `frontal-shoulder-1-candidate`는 사람 관절의 가시성, 정면 배치, 손 위치 안정성을 확인하고 어깨 이동을 어깨 너비로 나눠 판단한다. 빈 화면, 직립 자세, 부분 왕복, 휴식, 추적 단절을 검사하는 단위 검사를 추가했다.

`healthmith-frontend/tools/pushup-lab/run.mjs`는 개인 영상을 브라우저 파일로 열어 기존 픽셀 방식과 같은 프레임을 비교한다. 제품 경로는 아니며 영상·좌표를 외부 API에 보내지 않는다. 출력의 기준 횟수는 호출자가 제공한 값이며 팀원이 실제 정답을 확인해야 한다.

이형민이 이전에 제공한 두 영상도 로컬에서 확인했다. 프레임을 눈으로 비교한 잠정 기준은 각각 5회다. 팀원이 확정한 정답으로 간주하지 않는다.

| 영상 | 기존 픽셀 판정 | 새 관절 후보 | 해석 |
| --- | --- | --- | --- |
